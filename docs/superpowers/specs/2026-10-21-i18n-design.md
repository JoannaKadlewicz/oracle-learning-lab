# Polish and English: language switch for the whole app

Date: 2026-10-21. Status: the owner asked to proceed without questions; every call below is the builder's.

## Intent

The owner wants the app usable in Polish or English, switchable by the learner, and working end to
end: "allow for a language change to Polish or English … provide me a working solution".

Today the languages are mixed:
- The interface, the 751 questions, the 206 exercises and all notes are English.
- The 366 flashcards are Polish.

A language switch that only translated the buttons would leave every screen half in the other
language. So "working" means everything a learner reads follows the chosen language:
- the interface;
- server messages;
- questions, options and explanations;
- flashcards and their SQL sample comments;
- exercises and hints;
- topic, section and objective names;
- error explanations;
- notes.

## Goals

- G1. **A language setting with two values, English ("en") and Polish ("pl").** It is offered in
  three places:
  - in Settings, next to the theme control;
  - in the sidebar footer, as a compact control next to Settings;
  - on the sign-in, registration and password-reset pages.

  Changing it applies at once, by reloading the page, and is remembered.
- G2. **Remembering the choice.**
  - Signed in, the choice is saved in the user's settings on the server (`settings.language`), so
    it follows them to other devices.
  - Before sign-in, it is kept in the browser.
  - The first visit with no choice anywhere uses the browser's preferred language: Polish if it
    prefers Polish, otherwise English.
  - Choosing a language on the sign-in page carries into the account at the first sign-in, unless
    the account already has a choice.
- G3. **The whole interface is translated.** That covers:
  - every string the front end shows, including the sidebar, every view, dialogs, toasts, the exam
    picker, empty states, results, keyboard hints and charts;
  - the auth pages;
  - the document `lang` attribute;
  - dates and numbers, formatted for the language.

  Polish plurals use the correct three forms (1 pytanie, 2 pytania, 5 pytań).
- G4. **Server messages shown to a person are translated.** These are error and validation messages
  in the JSON `error` field (login, registration, password rules, rate limits, settings, practice
  database states and so on).
  - The server picks the language per request. A valid `X-Language` header sent by the app wins,
    then the `Accept-Language` header, then English.
  - Messages are translated at the web layer, so services keep raising plain English.
- G5. **Content follows the language.** English is the source for questions, exercises, notes, topic
  names and error explanations; Polish is the source for flashcards. Each item gets a translation
  into the other language:
  - **Questions:** prompt, every option, explanation, and the `--` comment lines of `try_sql`.
    Options that are SQL stay byte-identical, and so do `code` and all SQL.
  - **Exercises:** title, task, hint, hint2.
  - **Flashcards:** front, back, and the `--` comment lines of `try_sql`. The SQL statements stay
    byte-identical.
  - **Packs:** topic, section and objective names.
  - **Exams:** exam names and "about" text, and the home-note titles and blurbs.
  - **Error explanations:** the title and explanation of each ORA code.
  - **Notes:** every built-in note (docs/ and topics/), with code blocks and SQL unchanged.
- G6. **Translations are data, kept beside the source, and checked.** A test and
  `oracle-lab validate --static` fail when:
  - a translation is missing for any item or field;
  - an id is unknown;
  - an option count differs;
  - a `{placeholder}` set differs;
  - a flashcard sample's SQL differs once comments are removed;
  - a front-end or server string has no Polish catalog entry.

  A missing translation at runtime falls back to the source text, so a gap never breaks a screen.
- G7. **Nothing else changes.**
  - Answers, grading, scheduling, progress, ids, stored data and SQL behaviour are untouched.
  - English learners see exactly today's English text, except the flashcards, which they now see in
    English.
  - All existing tests pass.

## Non-goals

- More than two languages. The design must make a third language a matter of catalog and
  translation files only, but none is added.
- Translating what the database says: Oracle error texts (ORA-…) and SQL*Plus-style result lines
  ("1 row inserted.", "Table created.") stay as Oracle and SQL*Plus print them. The Oracle exams
  are taken in English, and these are the real messages learners must recognise.
- Translating SQL, identifiers, sample data or code blocks.
- Machine translation at runtime. Every translation is written ahead of time and committed.

## Anti-goals

- Any screen mixing languages when a translation exists.
- A translation that changes meaning:
  - a wrong answer becoming right;
  - an option reordered;
  - SQL inside text altered;
  - a technical term mistranslated so that it no longer matches the exam's English term.

  When a Polish term is unusual, keep the English SQL term in backticks or brackets, for example
  "złączenie (JOIN)".
- A stored-data migration, or a change to any existing environment variable.

## Constraints

- **Stack:** the same as today. Python 3.12 standard library, a vanilla-JS ES-module single-page
  app, and a strict CSP: inline scripts only through the existing hash mechanism, no inline
  handlers.
- **No new dependencies.** Polish plural rules come from the browser's `Intl.PluralRules` and a
  small server-side rule.
- **Voice:** Polish copy uses the informal "ty" form, matching the existing flashcards ("Wpisz go
  dwa razy"). It is plain and short, in the same voice as the English: sentence case, no
  exclamation marks.
- **Terminology:** Oracle and SQL terms stay in English where Polish practitioners use them (SELECT,
  JOIN, NULL, constraint names). Use the established Polish terms where they exist: "zapytanie"
  (query), "podzapytanie" (subquery), "transakcja", "indeks", "widok", "sekwencja", "wiersz",
  "kolumna", "tabela".

## The how, as decided (builder's calls)

- **Message catalogs keyed by the English source string**, in the gettext style.
  - The front end calls `t("Start the session")` and `t("Now preparing for {code}.", {code})`. The
    Python web layer calls `translate(lang, message)`.
  - English needs no catalog. The Polish catalogs are JSON:
    - `resources/static/i18n/pl.json` for the front end, public, because the auth pages need it;
    - `src/oracle_lab/i18n/pl.json` for the server.
  - A plural entry holds the three Polish forms, selected with `Intl.PluralRules("pl")` and an
    equivalent Python rule. English plural pairs stay in code as today.
- **Content translations are overlay files** under `src/oracle_lab/content/i18n/<lang>/`, keyed by
  item id and field.
  - The content layer returns items in the requested language. `for_exam(code, lang)` copies items
    and never mutates the source.
  - The pack declares each kind's source language: questions and labs "en", flashcards "pl".
- **Notes have a sibling file per language**, for example `notes.pl.md` next to `notes.md` and
  `cheat-sheet.pl.md`. The library path stays the English one, so links and saved references keep
  working, and the library serves the variant for the request's language.
- **Choosing a language reloads the page.** That is simplest and robust: content, catalogs and
  charts all load fresh.
- **Language detection on the server:** valid `X-Language` header, then `Accept-Language`, then
  "en".
- **Bulk translation** is done by parallel translator agents, one batch of topics each, each
  reviewed by a bilingual reviewer. They are written as committed data, and the validator gates
  them.

## Settled after the design check (builder's calls)

- **Who checks translations.** Agents translate and separate agents review, against a fixed
  glossary. Then the owner gets a short spot-check list: questions whose options or explanations
  quote literal output that a translation could break (TO_CHAR with 'Month', INITCAP and the like).
  - The infrastructure and the gate land first, and the gate is strict.
  - Content lands topic by topic on the same branch. The branch merges only at 100% coverage. The
    coverage test is added in the final task, after all batches.
- **A language clicked on a sign-in page during this visit wins.** It is saved to the account at
  sign-in. A detected or remembered default never overwrites the account's saved setting. The browser
  keeps a flag saying whether the choice was clicked.
- **Comments are translated wherever they sit in SQL shown to the learner:**
  - question `code` and `try_sql`;
  - flashcard `try_sql`;
  - `.sql` notes, as `.pl.sql` siblings.

  Each translation is checked to be the identical SQL once comments are removed. Comments inside
  fenced code blocks in Markdown notes are translated too, with the same rule for the SQL around
  them. That is stricter than the earlier wording, and avoids mixed screens.
- **Every new item needs its translation entry.** `generated.json` has no pipeline on this branch.
  AUTHORING.md says every new item needs its translation entry, and the gate stays strict for all
  items.

## How we'll know it worked

- Switching to Polski on the sign-in page shows that page in Polish. After sign-in, everything is in
  Polish:
  - Today, Quiz (questions, options, explanations), Flashcards (front, back, sample comments),
    Exercises, SQL lab, Mistakes, Progress, Notes, Settings, Admin;
  - error messages, toasts, dialogs and dates.
- Switching back to English shows exactly today's English, and the flashcards in English.
- Coverage tests report 100% for both languages.
- The full suite passes, including the database-backed run.
- A Polish browser on a first visit gets Polish, and an English one gets English.
