# Polish and English Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Learners can switch the whole app (interface, server messages, questions, flashcards, exercises, notes, error explanations) between English and Polish, with every translation committed, checked and complete.

**Architecture:**
- **Message catalogs.** Catalogs are keyed by the English source string. There is a server one (`src/oracle_lab/i18n/`) and a front-end one (`resources/static/i18n/pl.json`, loaded by `js/core/i18n.js`).
- **Language per request.** It comes from an `X-Language` header, then `Accept-Language`, then English. Error payloads are translated at the web layer.
- **Content overlays.** Content translations are overlay JSON files in `src/oracle_lab/content/i18n/<lang>/`, applied to copies by `content.for_exam(code, lang)`.
- **Notes.** Notes get `.pl.md`/`.pl.sql` siblings, served under the English path.
- **Validator.** It gains translation checks. A final coverage gate requires 100%.

**Tech Stack:** Python 3.12 stdlib, pytest and ruff; vanilla-JS ES modules with a strict CSP; `Intl` in the browser. No new dependencies.

**Spec:** `docs/superpowers/specs/2026-10-21-i18n-design.md`

## Global Constraints

**Languages**
- Exactly "en" and "pl". `DEFAULT_LANGUAGE = "en"`. A third language must need only new catalog and overlay files.

**Language choice**
- **Signed in:** `settings.language` in the user's state, validated against the languages.
- **Before sign-in:** browser localStorage key `study:lang`, plus `study:lang-explicit` = true when the learner clicked.
- **First visit:** `navigator.languages` starting with "pl" gives "pl", else "en".
- **At sign-in:** a language clicked on an auth page during this visit overwrites the account's setting. A detected or remembered default never does.
- **Applying a change:** changing the language reloads the page.

**Requests**
- The front end sends the header `X-Language: <lang>` on every fetch, including the auth pages.
- The server language is a valid `X-Language`, else the best `Accept-Language` match, else "en".

**What stays untouched**
- No stored-data migration. No env var change. Answers, ids, grading, scheduling and SQL behaviour don't change.
- Oracle error texts (ORA-…) and SQL*Plus result lines ("1 row inserted.", "Table created.") stay English.

**English mode**
- It is exactly today's text, with flashcards now in English.

**SQL**
- SQL is never translated: statements, identifiers, sample data, option texts that are SQL, `code`, `solution`, and the statements inside `try_sql`/`starter`.
- Only `--` comment lines and `/* */` comments in SQL shown to learners are translated.
- A translated SQL field must equal the source once comments are removed and whitespace is normalised.

**CSP and copy**
- CSP stays strict. Escape every interpolation with `esc()`.
- Copy is plain, sentence case, with no exclamation marks.
- Polish uses the informal "ty" form, matching the existing flashcards ("Wpisz…", "Sprawdź…").

**Interfaces:**
- Produces, in `oracle_lab.i18n`:
  - `LANGUAGES: tuple[str, ...] = ("en", "pl")`, `DEFAULT_LANGUAGE = "en"`.
  - `class Msg(str)`: a str whose value is the formatted English, with `.template: str` and `.params: dict`. Built with `Msg.of(template, **params)`.
  - `translate(lang: str, text: str) -> str`. For a `Msg` it translates the template, then formats it with the params. For a plain str it looks up the catalog. A missing entry or "en" returns the text unchanged.
  - `ntranslate(lang, n: int, one: str, many: str, **params) -> str`. English picks `one` when n == 1. Polish looks up `many` in the catalog, whose value is a list of 3 forms, and picks by `polish_form(n)`.
  - `polish_form(n: int) -> int`: 0 when n == 1; 1 when n % 10 in 2..4 and n % 100 not in 12..14; else 2.
  - `negotiate(header: str | None, accept_language: str | None) -> str`.
- Every user-facing server message whose text has variable parts becomes a `Msg.of(template, …)` at the raise site (e.g. "daily_minutes must be between {low} and {high}"). The Retry-After wording stays client-side as today.
- `Request.language: str` is set by a new middleware `language` (placed before `error_boundary`) using `negotiate(request.header("x-language"), request.header("accept-language"))`.
- `pl.json` holds a Polish entry for **every** user-facing message the server can send: auth, registration, password policy problems, account settings, admin, practice database states, settings validation, not-found errors, rate limits, and the 401/403/404/500 texts.

**Interfaces:**
- Produces, in `js/core/i18n.js`:
  - `export async function initI18n(lang)`: loads `/i18n/<lang>.json` for non-English and sets `document.documentElement.lang`.
  - `export function lang() -> "en" | "pl"`.
  - `export function t(msgid, params = {})`: catalog lookup, then `{name}` replacement. A missing entry returns the msgid formatted.
  - `export function tn(n, one, many, params = {})`: English is one/many; Polish uses the catalog's 3-form list for `many`, chosen with `new Intl.PluralRules("pl").select(n)` ("one" → 0, "few" → 1, "many"/"other" → 2). `{n}` is replaced with n.
  - `export function preferredLanguage()`: account setting (when signed in, passed in) → `localStorage study:lang` → `navigator.languages` → "en".
  - `export function rememberLanguage(code, { explicit })`.
  - `export function formatDate(date, options)` and `formatNumber(n)`, using `Intl` with `lang()`.
- `plural(n, word, many)` becomes `tn(n, "{n} " + word, "{n} " + (many ?? word + "s"))`, so existing call sites translate through catalog entries keyed "{n} questions" and so on.
- **Static extraction test** (`tests/test_i18n_frontend.py`). It scans `resources/static/js/**/*.js` for string-literal arguments of `t("…")`, `tn(n, "…", "…")` and `plural(n, "…", "…")` (also the template-literal form without `${`). Then it asserts:
  - every msgid (and every `{n} word` pair for plural) has a `pl.json` entry;
  - placeholder sets match;
  - plural entries are 3-item lists.

  It also checks the static auth HTML: every element with `data-i18n="msgid"` has an entry.

**Interfaces:**
- **Overlay files:**
  - `content/i18n/<lang>/<topic>.json` = `{"questions": {id: {...}}, "labs": {id: {...}}, "flashcards": {id: {...}}}`.
  - `content/i18n/<lang>/_pack.json` = `{"topics": {tid: name}, "sections": {sid: name}, "objectives": {oid: name}}`.
  - Allowed fields:
    - **question:** prompt, options (a list of the same length), explanation, code, try_sql;
    - **lab:** title, task, hint, hint2, starter, solution;
    - **flashcard:** front, back, try_sql.
  - `code`, `try_sql`, `starter` and `solution` are "SQL fields": they may differ from the source only in comments.
- **API:**
  - `content.i18n.load(lang) -> Overlay` (cached).

- **Validator:** `validate_content.translation_problems(lang: str, topic: str | None = None, complete: bool = False) -> list[str]` checks:

  - option-count mismatches;
  - SQL options changed (when the source option is SQL, i.e. it starts with a SQL keyword or `inlineCode`'s SQL pattern, the translation must be identical);
  - SQL fields differing once comments are stripped;
  - `{placeholder}` and backtick-span count mismatches;
  - empty strings;
  - with `complete=True`, every item and field missing a translation.

  The `.pl.md`/`.pl.sql` note siblings are checked too:
  - every fenced code block and every `.sql` file must match its English counterpart once comments are stripped;
  - with `complete=True`, every English note has a sibling.

  CLI: `validate --static --lang pl` runs it with `complete=False`; `--complete` adds completeness.
- **Error hints:** `error_hints.explain(..., lang="en")` localizes the title and explanation. The overlay `analysis/i18n/pl.json` is `{code: {"title", "explanation"}}`.
- **Delivery:**
  - `/api/content`, mock-exam reports and error explanations use `request.language`.
  - The notes endpoint passes the language.
  - The front end needs no change: it already renders what the server sends.
